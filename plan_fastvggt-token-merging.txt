================================================================================
Branch C, part 2: does FastVGGT's cross-view token merging transfer to DA3?
================================================================================

GOAL
----
FastVGGT (ICLR 2026, ../FastVGGT) is a TRAINING-FREE acceleration of VGGT: it
observes that the global (cross-view) attention maps of a visual geometry
transformer are highly redundant, and therefore merges most tokens together
BEFORE the global attention, runs attention on the merged (much shorter)
sequence, and un-merges the result back to full length. No retraining, no
checkpoint change, ~4x on 1000-frame ScanNet reconstructions at ~equal accuracy.

DA3's backbone is architecturally the same animal (alternating per-frame /
cross-view attention over a ViT), so the method should port almost verbatim.
This plan works out (a) exactly where it hooks into DA3, (b) the honest ceiling
on what it can buy DA3-SLAM, and (c) how to test it.

THE HEADLINE CAVEAT, UP FRONT
-----------------------------
FastVGGT's 4x comes from N^2 domination: at 1000 input frames the global
attention IS the model. DA3-SLAM runs submaps of 16 keyframes. The global
attention share of the forward pass — and therefore the entire prize — is a
function of submap size S, and at S=16 it is SMALL.

  Analytic FLOP model (nested-giant @504, TUM 640x480 -> 504x378 -> 36x27 grid,
  n = 973 tokens/frame, giant d=1536, 14 global blocks of 40):

    global-attention share of nested-giant FLOPs
      S=8   18%     S=32  46%
      S=16  30%     S=64  63%      S=128  78%

  Best-case speedup if merging cuts the global token count to ~35% (i.e.
  attention cost to 0.35^2 = 12%):
      S=16  1.36x   S=32  1.68x   S=64  2.25x   S=128  3.1x

  BUT the repo's own measurement disagrees with the FLOP model, in the
  pessimistic direction. outputs/kf_submap_grid/grid.csv gives per-frame submap
  latency 0.168 / 0.174 / 0.193 s at S = 8 / 16 / 32. Fitting t(S) = c + k*S
  gives k = 1.04 ms/frame/S, i.e. an EMPIRICAL global-attention share of only
  ~10% at S=16 and ~17% at S=32 — roughly a third of the FLOP model, because
  SDPA/flash attention runs at far higher hardware efficiency than the
  linear/MLP layers that dominate the rest.

  Empirical ceiling, then: ~1.10x at S=16, ~1.20x at S=32, ~1.35x at S=64.
  And that is BEFORE the merge/unmerge gather-scatter overhead, which is pure
  memory traffic and buys nothing back.

CONCLUSION THAT SHAPES THIS WHOLE PLAN: porting FastVGGT to accelerate the
CURRENT operating point is not worth it. The interesting question is the other
direction —

    FastVGGT does not make S=16 faster. It makes LARGE S AFFORDABLE.

  Peak memory at S=16 is 12.8 GB (T2) on a 20 GB card; S=32 does not fit. Global
  attention memory is what blocks it, and that is exactly what merging cuts.
  And larger submaps are a KNOWN accuracy lever in this system: every submap
  boundary is an anchor-frame composition + a metric-scale hop (CLAUDE.md,
  "two concepts that are non-obvious"), so halving the number of submaps halves
  the number of places drift can enter.

  So the claim to test is NOT "same accuracy, faster". It is:
      "merging buys a submap size we could not otherwise run, and that larger
       submap is more accurate at equal-or-lower latency and memory."
  That is a genuine SLAM-specific contribution, not a re-run of the FastVGGT
  paper on a different backbone.

COMPUTE: light-to-moderate. No retraining. Step 0 is an afternoon of profiling
and decides whether to continue at all.

--------------------------------------------------------------------------------
GLOSSARY
--------------------------------------------------------------------------------
  Local / frame attention .. attention within ONE frame's tokens. Tensor is
                       reshaped (b s) n c, so frames cannot see each other.
                       Cost ~ n^2, independent of submap size.
  Global / cross-view attention .. attention over ALL frames of the submap at
                       once. Tensor is b (s n) c. Cost ~ (S*n)^2. THE target.
  alt_start .......... the DA3 block index where alternating attention begins.
                       Blocks [0, alt_start) are pure per-frame encoder; from
                       alt_start on, ODD block indices are global and EVEN ones
                       are local. da3-giant: alt_start=13, depth=40.
  ToMe / bipartite soft matching .. the merging algorithm FastVGGT borrows from
                       ToMeSD. Tokens are split into a DESTINATION set (dst, a
                       strided sample kept intact) and a SOURCE set (src); each
                       src token is averaged into its most cosine-similar dst
                       token. r = how many src tokens get absorbed.
  merge_ratio ........ FastVGGT's r as a fraction of N. Default 0.9, which in
                       practice absorbs every src token.
  merging (int) ...... the block index from which merging is switched ON. 0 =
                       every global block. This is the accuracy/speed dial.
  Protection ......... FastVGGT keeps ~10% of tokens (a uniform stride over the
                       global index range) out of the merge, plus ALL of frame
                       0 and all per-frame special tokens.
  unmerge ............ scatter the attention output of a dst token back to every
                       src token that was absorbed into it. The residual stream
                       stays full-length; only the attention is short.
  The "triple" ....... (ATE, backbone latency, peak GPU memory), always reported
                       together — same convention as plan_static-compute-
                       reduction.txt.

================================================================================
PART 1 -- THE MAPPING: FastVGGT -> DA3 (what the port actually is)
================================================================================

WHERE FASTVGGT LIVES (3 files, ~300 lines that matter)
  ../FastVGGT/merging/merge.py
      token_merge_bipartite2d(metric, w, h, sx, sy, r, no_rand, generator,
                              enable_protection) -> (merge_fn, unmerge_fn)
      The whole algorithm. Backbone-agnostic EXCEPT for one hardcoded line:
          tokens_per_img = w * h + 5
      (5 = VGGT's 1 camera + 4 register tokens.)
  ../FastVGGT/vggt/layers/attention.py
      Attention.forward(x, pos, global_merging): if global_merging is not None,
      build (m, u) from x, merge q/k/v (m applied to all three via the
      extra_tensors / extra_tensors_2 arguments), run SDPA on the short
      sequence, project, then x = u(x). ~40 lines.
  ../FastVGGT/vggt/models/aggregator.py
      Bookkeeping only: passes global_merging=block_num into global blocks once
      block_num >= self.merging.

WHERE IT LANDS IN DA3
  Depth-Anything-3/src/depth_anything_3/model/
    dinov2/vision_transformer.py :: DinoVisionTransformer
        ._get_intermediate_layers_not_chunked()  <- the block loop
        .process_attention(x, blk, "global"|"local", pos, attn_mask)
    utils/block.py     :: Block.forward(x, pos, attn_mask)
    utils/attention.py :: Attention.forward(x, pos, attn_mask)   <- THE HOOK

  For the default nested-giant, the anyview branch (da3-giant.yaml) is a
  40-block vitg with alt_start=13, so the GLOBAL blocks are the odd indices
      i = 13, 15, 17, ..., 39   ->  14 global blocks of 40.
  Each DA3 block is used for exactly ONE attention type (unlike VGGT, which has
  two separate ModuleLists), so the port is simply: identify those 14 blocks,
  wrap their .attn.forward.

  In DA3-SLAM this must be done as a RUNTIME PATCH, not an edit to the
  Depth-Anything-3 checkout — that checkout is gitignored and re-cloned by
  setup.sh, so edits there vanish on rebuild. The precedent already exists and
  should be copied: da3_slam/backend/inference/token_tap.py attaches hooks to
  the SAME block loop (blocks [0, alt_start), the frame-independent prefix) and
  documents the pattern, including per-thread arming via threading.local so the
  concurrent loop-closure re-inference is unaffected. A new
  da3_slam/backend/inference/token_merge.py should mirror it exactly.
  The two compose cleanly: the tap owns blocks < 13, merging owns odd blocks
  >= 13. They never touch the same block.

SEVEN CONCRETE DIFFERENCES THE PORT MUST HANDLE
  1. SPECIAL TOKENS PER FRAME. VGGT: 5. DA3: patch_start_idx = 1 and
     num_register_tokens = 0 (DinoV2 in DA3 never passes it), so
         tokens_per_img = w*h + 1.
     merge.py's `+ 5` must become a parameter. Everything downstream (the
     cls_indices block that marks special tokens as dst) follows from it.
     The single special token is the CAMERA TOKEN — vision_transformer.py does
     `x[:, :, 0] = cam_token` at i == alt_start, and cam_dec reads feats[-1][1]
     (index 0 of each frame at block 39) to produce the pose. It is already in
     the dst set, so it is never absorbed. Good; see risk R1 below anyway.

  2. THE PATCH GRID IS NOT SQUARE-FRIENDLY. At process_res 504, TUM 640x480 is
     upper_bound_resize'd to 504x378 -> 36 x 27 patches. sy=2 does not divide
     27: FastVGGT's `effective_h = min(hsy*sy, h)` silently leaves the bottom
     patch row unassigned, so the last row of every frame becomes src. Not a
     crash, but it is an undocumented asymmetry. Either pass sy=1 for odd
     heights or extend the remainder handling. Also note FastVGGT calls
     model.update_patch_dimensions(w, h) per scene — the grid is per-batch
     data, not a constructor constant, and the DA3 port needs the same because
     DA3 resolution is a swept knob (SharedSLAM.set_resolution).

  3. ROPE IN GLOBAL BLOCKS IS A NO-OP IN DA3 (and this is good news).
     _prepare_rope builds two position tensors. Local blocks get `pos` (real 2D
     patch coordinates). Global blocks get `pos_nodiff`, which is ONES for every
     patch token and ZERO for the special token. So DA3's cross-view attention
     carries no spatial position at all — it is permutation-invariant over patch
     tokens. Consequences:
       - merging destroys no positional information here, unlike in VGGT where
         global attention does use real 2D RoPE. The port is strictly SAFER.
       - the (sx, sy) spatial grid used to pick dst is therefore only a
         heuristic for spreading dst evenly over the image, nothing more.
       - it also makes FastVGGT's founding observation (global attention maps
         are highly redundant across tokens) a priori MORE likely in DA3.
     Verify this empirically in Step 1 rather than trusting the reading.

  3b. THE SHIPPED YAML MODEL CANNOT MERGE AT ALL. config/default.yaml sets
     depth_model: DA3METRIC-LARGE, which is configured alt_start = -1 -- no
     cross-view attention, so TokenMerger refuses it outright. Every merging
     experiment must pass --depth_model nested-giant (or giant/large), the same
     model the benchmarks and the Branch B results already use.

  4. THE METRIC BRANCH IS OUT OF SCOPE. nested-giant = DA3-GIANT (anyview) +
     DA3METRIC-LARGE (metric). The metric branch is configured alt_start = -1,
     i.e. it has NO cross-view attention whatsoever. Merging cannot touch it.
     It is ~20% of nested-giant's latency (T2: giant 19.1 s vs nested-giant
     23.8 s on TUM), so it is a hard floor on any speedup: even infinitely fast
     global attention leaves that 4.7 s. (It IS the target of a different
     Branch C idea — it is frame-independent end to end, so it is a pure
     temporal-reuse opportunity. Different plan.)

  5. ALL FOUR DPT TAPS ARE GLOBAL BLOCKS. da3-giant out_layers = [19, 27, 33,
     39] — every one is odd, i.e. every one is a global block, and cat_token
     concatenates the preceding local output. So merging degradation feeds the
     depth head at all four scales AND the pose head. There is no "safe" head.

  6. REFERENCE-VIEW REORDERING ALREADY PUTS THE ANCHOR AT INDEX 0. At
     i == alt_start - 1, when S >= THRESH_FOR_REF_SELECTION (=3) and no camera
     conditioning is supplied (DA3-SLAM supplies none), select_reference_view /
     reorder_by_reference move the chosen reference view to index 0.
     FastVGGT independently marks frame 0 entirely as dst. Those two decisions
     agree, and in DA3 the choice is principled rather than arbitrary. Keep it.

  6b. THERE ARE TWO `Attention` CLASSES IN DA3 AND THE OBVIOUS ONE IS THE WRONG
     ONE. `model/utils/attention.py` is NOT what the ViT uses; the blocks come
     from `model/dinov2/layers/`, whose Attention keeps `head_dim` as a local
     (derive it as C // num_heads), carries a `fused_attn` flag with a manual
     softmax fallback, and guards RoPE on `pos is not None`. Copying the
     `model/utils` version gives a module that looks right and fails on the
     first attribute access. The drift guard in token_merge.py exists because
     of this and caught it on the first GPU run.

  7. attn_mask. DA3's Attention.forward accepts attn_mask and passes it to SDPA.
     Merging changes the sequence length, so a non-None mask would be silently
     wrong. DA3-SLAM never passes one (kwargs.get("attn_mask", None) is always
     None from da3.py), but the port must assert this, not assume it.

RISKS SPECIFIC TO USING THIS FOR SLAM
  R1. POSE IS THE OUTPUT THAT MATTERS HERE, AND POSE IS THE MOST FRAGILE.
      FastVGGT's headline evaluation is Chamfer distance on ScanNet point
      clouds; it does report ate/are/rpe_rot/rpe_trans (eval/eval_scannet.py),
      but reconstruction is the pitch. DA3-SLAM's headline is Sim3 ATE.
      AND THE CAMERA TOKEN IS WORSE OFF THAN "EXACT QUERY, APPROXIMATE CONTEXT":
      being a merge DESTINATION means never being absorbed into another token,
      NOT being left untouched. ToMe's merge is a symmetric mean, so a
      destination that absorbs sources becomes the mean of itself and them --
      the camera token's own q/k/v are averaged with whatever patch tokens land
      on it, and cam_dec reads exactly that token (feats[-1][1]) to produce the
      pose. Verified in scripts/test_token_merge.py. Measure pose directly and
      early (Step 1); the first measurements above already put it at 280x the
      bf16 noise floor at FastVGGT's own default setting.
  R2. SMALL BATCHES. The loop-closure worker re-infers 2 + 2*context_frames
      (~4) frames. Merging there saves nothing and risks accuracy on the exact
      inference that decides whether a closure is accepted. Gate merging on a
      minimum S; leave loop-closure re-inference unmerged. (The token_tap's
      per-thread arming already gives the mechanism.)
  R3. NON-DETERMINISM. FastVGGT seeds its dst sampling (manual_seed(33)) so
      merging is reproducible, but it is a NEW source of config-dependent
      variance on top of the bf16 non-determinism the Branch B plan already
      insists on handling with N>=3 repeats. Keep the seed fixed AND keep the
      repeats; optionally sweep the seed once to size the merge-pattern
      variance separately.
  R4. A SUBTLETY IN FastVGGT's PROTECTION SET. protected_indices is a uniform
      stride over ALL N global indices (`torch.arange(0, N, step)`), so it
      overlaps the dst set and the special tokens. Those tokens then appear
      TWICE in the merged sequence — once with merge-averaged q/k/v, once
      untouched — which double-counts them in the attention denominator; the
      unmerge scatters the protected copy last, so it wins. This ships in
      FastVGGT and evidently works, but it is an accident of their token
      layout. With DA3's different tokens_per_img it should be checked, and
      `enable_protection=False` is a cheap ablation to run.
  R5. WALL-CLOCK vs FLOPs. Merging replaces a dense, high-arithmetic-intensity
      SDPA call with a shorter SDPA plus several gather/scatter passes that are
      pure memory traffic. The measured share above already says the FLOP model
      over-promises by ~3x. Report wall-clock only; FLOPs are a sanity proxy.

================================================================================
PART 2 -- THE MECHANISM: a DA3-SLAM module, zero edits to Depth-Anything-3
================================================================================

The whole port fits in one new file, `da3_slam/backend/inference/token_merge.py`,
plus a vendored copy of the merge kernel. Nothing under `Depth-Anything-3/` is
touched. This is not a workaround — it is the same thing `token_tap.py` already
does to the same block loop of the same model, and its model-introspection
helpers are reusable verbatim.

WHY IT WORKS AT ALL
  The merge is a per-block, per-call transformation of ONE tensor. It needs
  exactly three things, and all three are reachable from a loaded model object:
    (a) which blocks are global   -> vit.alt_start + the odd-index rule;
    (b) the patch grid and frame count of the current batch
                                  -> the DinoV2 wrapper's (B, S, 3, H, W) input;
    (c) a place to intervene inside attention
                                  -> the block's `.attn` submodule.
  `token_tap.py` already solves (a) and (b) and its resolvers can be imported
  as-is:
      _resolve_net(model, "anyview")       # api wrapper -> nested -> .da3
      _resolve_backbone(model, "anyview")  # the DinoV2 wrapper (sees B,S,3,H,W)
      _resolve_vit(model, "anyview")       # DinoVisionTransformer: .blocks, .alt_start
  Global blocks are then
      [i for i in range(len(vit.blocks)) if i >= vit.alt_start and i % 2 == 1]
  read off the loaded model — never hardcoded, so it follows model size
  automatically (giant: 14 of 40; large: alt_start 8, depth 24 -> 8 of 24).

THREE POSSIBLE MECHANISMS (pick M1; M2 is the cheap variant; M3 is a different
method wearing the same clothes)

  M1 -- MODULE SWAP.  blk.attn = MergingAttention(blk.attn)
    A small nn.Module that holds the ORIGINAL attention's submodules by
    reference (qkv, q_norm, k_norm, proj, proj_drop, rope, num_heads, head_dim)
    and reimplements the ~15-line forward with the merge spliced in:
        norm1(x) -> qkv -> qk_norm -> rope -> MERGE(q,k,v) -> SDPA -> proj
                 -> UNMERGE
    * Bit-exact reproduction of FastVGGT's operation order, which is what makes
      a Step-1 accuracy result attributable to the METHOD rather than to your
      variant of it.
    * Fully reversible: `blk.attn = blk.attn.inner`. No weights are copied, so
      swapping in and out is free and the sweep can flip merging on/off on a
      model that stays loaded (SharedSLAM reuses one model across configs).
    * Cost: duplicates ~15 lines of DA3's Attention.forward, so it can drift if
      setup.sh re-clones a changed upstream. Guard it — see DRIFT GUARD below.
    RECOMMENDED as the primary implementation.

  M2 -- PURE PRE/POST HOOKS on blk.attn.  No duplicated code at all.
    pre-hook  (with_kwargs=True): build (m, u) from the incoming x, return
                                  (m(x),) and a `pos` gathered down to the
                                  merged index set;
    post-hook (with_kwargs=True): return u(output).
    DA3's own unmodified Attention.forward runs on the short sequence in
    between. This is EXACTLY equivalent to M1 for the linear parts, because the
    qkv projection is affine:
        Linear(mean(x_i)) = W*mean(x_i) + b = mean(W*x_i + b) = mean(Linear(x_i))
    so merging the input and then projecting gives precisely FastVGGT's
    mean-merged q/k/v. It differs in exactly two places:
      - `qk_norm` (LayerNorm, nonlinear) applies AFTER merging instead of
        before. Second-order for near-identical tokens — which is the premise
        of merging in the first place — but it is a real difference;
      - RoPE applies to the merged tokens' gathered positions rather than
        pre-merge. In DA3 this is a non-issue for patch-to-patch merges because
        global positions are UNIFORM (difference #3: pos_nodiff is all-ones for
        every patch token), and bites only for a patch token absorbed into a
        camera token (pos 0).
    * Zero duplication, pure public nn.Module hook API, needs no drift guard.
    * Worth implementing as a flag on the same module and ablating in Step 1:
      if M2 matches M1 inside the noise band, keep M2 and the implementation
      becomes maintenance-free.

  M3 -- HOOK THE WHOLE BLOCK (merge before norm1, unmerge after the MLP).
    Tempting, because it would also shorten the MLP — 16*d^2 per token, the
    single largest term in the forward, far bigger than the attention this plan
    is chasing. But it is NOT FastVGGT: it collapses the residual stream, so
    every absorbed token receives the destination token's entire block output
    rather than its own residual. That is a strictly more aggressive method
    with a different accuracy profile.
    Do not ship it as "the port". Note it as a follow-up idea and, if Step 1
    shows DA3 tolerates merging easily, test it as its own hypothesis — the
    upside is much larger than FastVGGT's, precisely because it attacks the
    term that actually dominates at S=16.

WHAT THE MODULE OWNS (all of it inside da3_slam/)
  1. `_tome.py` — vendored from ../FastVGGT/merging/merge.py, with
     tokens_per_img parameterised (w*h + patch_start_idx + num_register_tokens
     instead of the hardcoded w*h + 5) and the odd-patch-height remainder
     handled (difference #2). The file imports nothing but torch, so it
     vendors cleanly. LICENSING: FastVGGT ships under Meta's *VGGT License*
     (research-use terms), not Apache-2.0 — keep its header, do not relabel it
     under this repo's MIT. If that is a problem, bipartite soft matching is
     ~80 lines and can be reimplemented from the ToMe paper.
  2. `token_merge.py` — discovery (reusing token_tap's resolvers), the M1/M2
     wrapper, arming, and the knobs.
  3. Per-batch geometry: a forward_pre_hook on the DinoV2 wrapper reads
     (B, S, 3, H, W) and stores w = W // patch_size, h = H // patch_size, and
     S for the call. This is DA3's equivalent of FastVGGT's per-scene
     model.update_patch_dimensions(w, h), and it makes the module automatically
     correct across the resolution sweep (SharedSLAM.set_resolution) instead of
     hardcoding a 36x27 grid. Copy `_on_backbone_start` from token_tap.
  4. Per-thread arming (threading.local), same as the tap: the loop-closure
     worker shares one DepthEstimator with the inference thread, and its ~4-frame
     re-inference must never be merged (R2). Gate on a minimum S there too.
  5. Knobs: merging start expressed as a POSITION AMONG THE GLOBAL BLOCKS (0-13
     for giant), not a raw block index — that is the unit that transfers across
     model sizes; plus merge_ratio, sx, sy, enable_protection, seed, min_frames.

DRIFT GUARD (M1 only)
  The Depth-Anything-3 checkout is gitignored and re-cloned by setup.sh, so an
  upstream change could silently invalidate the duplicated forward. On attach,
  assert the attention module still has the attributes the copy assumes
  (qkv, q_norm, k_norm, proj, proj_drop, rope, num_heads, head_dim) and that
  attn_mask is None (difference #7); optionally hash inspect.getsource of the
  upstream Attention.forward and warn loudly on mismatch. M2 needs none of this.

INTERACTION WITH THE EXISTING TAP
  None. The tap hooks blocks [0, alt_start); merging wraps odd blocks
  >= alt_start. They never touch the same block and can be armed together.
  The reference-view reorder at i == alt_start - 1 happens in the block LOOP,
  not in a block, and permutes frames before the first global block — so by the
  time the wrapper sees (B, S*n, C), index 0 is already the reference view,
  which is exactly the frame FastVGGT wants held out as destination (#6).

STATUS -- the module is BUILT; first measurements are in
================================================================================

Implemented (M1, nothing under Depth-Anything-3/ touched):
  da3_slam/backend/inference/_tome.py         vendored merge kernel
  da3_slam/backend/inference/token_merge.py   TokenMerger + MergingAttention
  da3_slam/config.py                          TokenMergingConfig + CLI helpers
  config/default.yaml                         token_merging: block (enable: false)
  scripts/test_token_merge.py                 kernel + model smoke test

  scripts/sweep_merging.py                    the Step-2 grid driver
  scripts/report_merging.py                   tables + figures from its rows

  On/off:  --token_merging / --no_token_merging  (run_slam.py and every
           benchmark_*.py), YAML token_merging.enable, or
           SharedSLAM.set_token_merging(cfg) for a sweep on a resident model.
           OFF detaches the wrapper entirely.

  Step 2 is therefore runnable as written:
      python scripts/sweep_merging.py --seq_dir <the 4 UAS GT sequences> \
          --submap_sizes 16 24 32 48 --merge_starts off 0 7 --repeats 3 \
          --seqcache outputs/sweep/step1_uas_resolution/_seqcache \
          --out_dir outputs/merging
      python scripts/report_merging.py --rows outputs/merging/merging_rows.jsonl \
          --out_dir outputs/merging
  It freezes keyframes once per sequence and replays them across the whole grid
  (without that control, submap_size also moves keyframe SELECTION through
  keyframe.max_submap_size and every ATE difference is confounded), records OOM
  cells with their high-water memory instead of dropping them, and reports UAS
  ATE as % of GT path length.

FIRST MEASUREMENTS (nested-giant @504, fr1/xyz, ONE 16-frame batch, no repeats —
indicative only, not a benchmark):

  bf16 noise floor over two unmerged runs:  depth 2.3e-03 m,  pose 2.3e-05
  realised token ratio: 0.389  (attention cost ~0.151x in merged blocks)

    merge start   backbone s   d depth      d pose      d pose / noise
    off (base)        2.726    2.3e-03      2.3e-05           1x
    block  0/14       2.614    1.02e+00     6.49e-03        280x
    block  4/14       2.692    7.76e-01     4.13e-03        178x
    block  7/14       2.696    5.23e-01     3.80e-03        164x
    block 10/14       2.713    5.94e-01     2.15e-03         93x
    block 13/14       2.731    5.19e-02     1.32e-03         57x

Two things fall straight out, and both were predicted above:

  1. THE SPEEDUP IS ~4% AT S=16, EVEN MERGING EVERY GLOBAL BLOCK. 2.726 ->
     2.614 s, while the merged blocks' attention dropped to ~15% of its cost.
     This is the empirical version of the Step-0 argument: at a 16-frame submap
     the cross-view attention is ~10% of the forward, and the merge/unmerge
     gather-scatter eats most of what it saves.  The "same config, faster"
     framing is dead on arrival; Step 2's large-submap framing is the study.

  2. THE DEVIATION IS LARGE AND POSE IS THE SENSITIVE OUTPUT.  At FastVGGT's own
     default (start=0, ratio 0.9) the pose deviation is 280x the bf16 noise
     floor, and even merging ONLY THE LAST global block leaves it at 57x.  The
     deviation does fall monotonically as merging starts later, so the knob
     behaves, but there is no obviously free setting.  Note this is a raw
     backbone deviation, NOT an ATE result — the pose graph may well absorb it,
     which is exactly what Step 1 has to establish against the noise band, on
     real sequences, with repeats.

SECOND MEASUREMENT — AND IT UNDERCUTS STEP 2's PREMISE
(sweep_merging.py smoke run: nested-giant @504, UAS frozen_lake, first 2500
frames, 257 frozen keyframes, loop closure off, ONE repeat — the ATE column is
not conclusive, but the MEMORY column is, because peak memory is a
near-deterministic quantity that does not need repeats.)

    16      off      5.30      18        45.3      12396.8      —

  MERGING DOES NOT REDUCE PEAK MEMORY. Not by a little — by 1 MB out of 12.4 GB

  token count in the merged blocks fell to 0.39x. The whole "merging makes a
  larger submap affordable" argument rests on merging relieving the memory
  wall, and it does not.

  Why, in hindsight: SDPA/flash attention is already O(N) in memory, not
  O(N^2), so shortening the sequence saves little that was ever allocated; the
  residual stream stays full-length through every block regardless; the merge
  itself allocates flattened q/k/v plus merged copies, which gives back most of
  what it saves; and the peak is evidently set somewhere else entirely (the DPT
  head decoding four full-resolution feature maps, and/or the per-frame token
  tensor across all frames). Step 0's profiling should now be pointed at
  WHERE the peak actually is, because that — not attention — is what gates
  submap size.

  Note also that ATE got WORSE with the larger submap in both arms here
  (5.30 -> 8.67 baseline), which is the opposite of Step 2's H2. One truncated
  sequence with loop closure off proves nothing, but combined with the mixed
  evidence already in outputs/kf_submap_grid/grid.csv it is a warning that the
  "fewer boundaries = less drift" story may not survive contact with data.

are stable to ~1%):

   16      2.70    12.10       2.64       12.11  0.389     1.02x       1.00x

  BOTH ARMS OOM AT THE SAME SUBMAP SIZE.  Merging does not move the memory wall

  was an inference of ours that the measurement does not support.

WHY FASTVGGT WORKS ON VGGT: IT IS SEQUENCE LENGTH, NOT THE ARCHITECTURE
Global-attention share of per-token FLOPs, from the two repos' actual configs
(VGGT: DINOv2 ViT-L patch_embed 24 blocks + 24 aggregator blocks doing frame
AND global attention, d=1024, 1041 tokens/frame.  DA3 nested-giant: 26 local +
14 global at d=1536, plus a 24-block metric branch at d=1024 with NO global
attention at all, 973 tokens/frame).  "max speedup" applies the measured token
ratio 0.389 to the merged blocks:

      S      VGGT share   max speedup      DA3 share   max speedup
      8           28.9%         1.32x          17.7%         1.18x
     16          44.8%         1.61x          30.0%         1.34x
     17          46.3%         1.65x          31.3%         1.36x
     32          61.9%         2.11x          46.2%         1.64x
    128          86.7%         3.78x          77.4%         2.92x
   1000          98.1%         5.96x          96.4%         5.50x

  Read the last row against the first few.  FastVGGT evaluates at
  --input_frame 1000, where global attention is 98% of VGGT and essentially
  the whole model; that is where "up to 4x" comes from.  At S=16-17 — which is
  VGGT-SLAM's OWN default (main.py:27, submap_size=16 + 1 overlapping frame) —
  the ceiling is 1.65x, and the FLOP model overstates reality by ~3x on this
  hardware (attention runs at far higher efficiency than the linear layers:
  we measured 1.02x against a 1.34x ceiling at S=16, 1.10x against 1.64x at
  S=32).  So FastVGGT applied to VGGT-SLAM would buy roughly what it buys us:
  a few percent.

  The architecture difference is real but SECONDARY — a 1.5x gap in attention
  share at S=16 (45% vs 30%), from three compounding causes:
    1. VGGT makes 24 of its 48 aggregator blocks global (50%); DA3-giant makes
       14 of 40 (35%).
    2. VGGT is d=1024, DA3-giant d=1536.  Linear cost scales d^2 but attention
       scales d, so the wider model buries attention 1.5x deeper.
    3. nested-giant carries a whole second branch (metric, 24 blocks) with
       alt_start=-1 — zero global attention, pure dead weight for merging.
  Closing all three would move DA3 from 30% to VGGT's 45% at S=16, i.e. from a
  1.34x ceiling to 1.65x.  Not the difference between "works" and "doesn't".

DECISION FOR THIS BRANCH
  The method is correctly ported and verified; the regime is wrong.  Merging
  pays only when the batch is long enough for cross-view attention to dominate
  (S >~ 128), and SLAM submaps are 16-32 by construction — and cannot be grown,
  because merging does not move the memory wall.  DO NOT RUN STEP 2 AT SCALE.
  Report the negative result: it is a clean, quantified statement about where a
  VGT-based SLAM system's compute actually is, it explains a published 4x
  without contradicting it, and it applies to VGGT-SLAM as much as to DA3-SLAM.

Module-boundary sampling of torch.cuda.max_memory_allocated (monotonic between

  PEAK 11,819 MB

  the head working at pixel resolution: 4 frames at 280/392/504 gives

    fp32                                    10272       96.8              106

    bf16+merge                               5606       75.0               75

  THREE THINGS FALL OUT.

  1. MEMORY IS CONSTANT-DOMINATED ACROSS EVERY SUBMAP SIZE ANYONE WOULD USE.
     The frame-independent floor equals the frame-dependent part only at
     N ~ 106 (fp32) / 111 (bf16).  Below that — i.e. at every submap size this
     system runs — you are mostly paying a fixed cost.  The measured wall is
     between 48 and 64 frames for fp32, and between 128 and 192 for bf16
     backbones (the linear fit's "max N" is optimistic; fragmentation and
     transient spikes bring the wall in earlier).

  2. MERGING NEVER SAVES MEMORY, AND AT LONG SEQUENCES IT COSTS MEMORY.
     Identical to within 5 MB up to N=48, then it goes the wrong way:
     +175 MB at N=64, +1534 MB at N=96, +2220 MB (+16%) at N=128.  The
     merge/unmerge buffers (flattened full-length q/k/v plus their merged
     copies) grow with N faster than the shortened attention saves, so merging
     LOWERS the maximum usable sequence length — the fit puts the bf16 ceiling
     at N~240 without merging and N~185 with it.  Merging is memory-negative at
     exactly the lengths where it was supposed to help.

  3. THE SPEEDUP IS REAL AND GROWS WITH N, EXACTLY AS THE SEQUENCE-LENGTH
     EXPLANATION PREDICTS: 1.01x at N=16 -> 1.09x at 32 -> 1.24x at 64 ->
     1.51x at 128.  This is the empirical confirmation of the VGGT comparison
     above: FastVGGT's mechanism is genuine, it simply needs sequence lengths
     that submap-based SLAM never uses.  (The FLOP ceiling overstates the
     measurement by ~1.5-2x throughout, as expected.)

  So for long sequences the honest summary is: merging buys ~1.5x speed at
  N=128 in exchange for ~16% more memory — a real trade, but one that only
  exists at submap sizes 4-8x larger than DA3-SLAM uses, and the earlier UAS
  smoke test found larger submaps made ATE worse, not better.

VERIFICATION
================================================================================
  1. Merging OFF must reproduce the current baseline EXACTLY (bitwise, same
     seed) — the wrapper is inert unless armed. If it is not, the port has a
     side effect and nothing after this is trustworthy.
  2. The loop-closure worker's re-inference is never merged (assert on S, and
     check the per-thread arming with the concurrency check that
     test_token_hook.py already uses for the tap).
  3. attn_mask is None on every merged block (assert, do not assume).
  4. Frozen keyframes: merged and unmerged runs at the same S produce
     byte-identical processed-frame lists.
  5. Every ATE is mean +- std over N >= 3 repeats; a config wins only beyond
     that band. Merging adds its own variance source (R3) — seed it, and size
     it once with a seed sweep.
  6. Report WALL-CLOCK backbone latency and PEAK MEMORY. FLOPs are a sanity
     proxy only, and Step 0 exists precisely because the FLOP model over-
     promises here by roughly 3x.
  7. Any OOM cell is recorded, not silently dropped — the OOM pattern is the
     evidence for the method.
