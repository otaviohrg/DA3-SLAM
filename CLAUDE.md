# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DA3-SLAM is a monocular RGB SLAM system built on top of **Depth Anything 3 (DA3)**. It feeds batches of keyframes through DA3 to get per-frame metric depth, confidence, and camera poses, assembles them into local **submaps**, stitches submaps into a global **SL(4) pose graph** (GTSAM), and closes loops via DINOv2/SALAD descriptor retrieval + DA3 re-inference. The architecture deliberately mirrors **VGGT-SLAM** (frame overlap, SL(4) factor graph, loop-closure wiring) — comments throughout reference that lineage, and it is the right mental model when reasoning about design choices.

## Environment & setup

- Python **≥3.11**, CUDA 12.8, PyTorch 2.10. GPU required (DA3 + DINOv2 inference).
- Two heavy dependencies are **not on PyPI** and are cloned + installed from source by `setup.sh` into `/opt/third_party`: [Depth-Anything-3](https://github.com/ByteDance-Seed/Depth-Anything-3) (provides `depth_anything_3.api`) and [SALAD](https://github.com/Dominic101/salad). Plain `pip install -r requirements.txt` is **not sufficient** — the pipeline will fail at `import depth_anything_3` without these.
- `uv` is the package manager. `setup.sh` assumes the repo is mounted at `/app` (Docker layout). The `Dockerfile` builds the full CUDA environment and runs `setup.sh`.
- GTSAM must be a build with **SL4 support** (`gtsam.SL4`, `PriorFactorSL4`, `BetweenFactorSL4`). Stock PyPI `gtsam` may not have these symbols — if `factor_graph.py` fails to import, that's why.

The **live camera** entry point is `scripts/run_realsense.py` (monocular RGB). It reuses the streaming machinery: `RealSenseFrameSource` (`scripts/realsense_source.py`, lazy `pyrealsense2`) yields `FrameItem`s into `DA3SLAM.run_stream(source, on_update=viewer)`. `on_update` is an optional per-submap callback (added to `run_stream`/`_processing`) carrying a `SLAMUpdate` (current trajectory + the new submap's world points + per-frame camera-space points in `frame_points_cam`); `LiveViewer` (`scripts/live_viewer.py`, lazy `rerun-sdk`) logs it, caches each submap's camera-space points, and **re-projects already-drawn submaps whenever their poses shift** (loop closure / later optimisation) — without that, corrected geometry stays frozen and every closure looks like a duplicated map. `run_realsense.py` also overrides the benchmark-tuned defaults for the live domain (`set_defaults`: `submap_overlap` 2, `boundary_scale_deadband` 0.25, `between_huber_k` 1.345, loop distance 0.6, gap 2, top-3, confidence 0.2, translation gate 3 m, blur gate `sharpness_window` 2 / `min_sharpness_ratio` 0.5) — explicit flags still win. The camera source sets auto-exposure *priority* off (exposure capped at the frame budget → less motion blur at constant fps); `--exposure` switches to manual exposure for aggressive anti-blur. In Docker the Rerun **viewer runs on the host** (`make viewer`) and the container connects out to it at `127.0.0.1:9876` — the `realsense` service uses `network_mode: host`, so no X11 and no gateway/`host.docker.internal` reachability issues. Ctrl-C sets a stop-event so the stream ends cleanly and the final optimisation + save still run. Demo tip: `--selection_mode disparity` (lower latency than the segment default). The `realsense` compose service adds USB passthrough (`privileged` + `/dev/bus/usb`); demo deps live in `requirements-realsense.txt` (installed by `setup.sh`).

`scripts/make_video.py` renders an **offscreen video** of a run (`make video`), for talks/demos where the Rerun viewer is not an option. It is the same `on_update` hook `live_viewer.py` uses, split in two: a recorder caches each submap's *camera-space* points plus every keyframe pose (cheap — a slow callback backpressures the SLAM threads), then a numpy/cv2 painter's-algorithm renderer replays them on a clock. Because the points are cached in camera space and re-projected with the newest poses at each video frame, a loop closure visibly snaps the map together instead of leaving a ghost copy — the same reason `LiveViewer` caches. The recording is saved next to the video, so `--render_only` re-renders with different camera/trail settings without touching the GPU. **Pose-graph corrections are eased, not stepped** (`--correction_ease`, default 0.5 s, 1.5 s for KITTI): an optimisation moves every keyframe at once, so the trail and the cloud teleport into their new shape. `_display_poses` holds the pose set currently on screen and approaches the newest snapshot exponentially (~95% inside the window), which renders a closure as the whole estimate bending into a better fit. Two details are load-bearing. It eases **from what is displayed**, not between consecutive snapshots: a correction landing while the previous one is still in flight otherwise snaps the trail back to the older shape first, and the longer the window the bigger that snap-back — which is why the first version measured an unchanged 5.61 m worst case at every window length. And it **snaps when the remainder falls under ~1 screen pixel** (1e-3 of the trajectory extent, so it suits both a 4 m room and a 500 m KITTI loop), for the same reason the framing ease settles in finite time. Measured worst single-frame trail motion, off → on: KITTI 06 46.05 → 2.97 m, teddy 13.2 → 2.4 cm, chess 1.7 → 0.3 cm, Replica 1.1 → 0.4 cm. It costs render speed, since a morphing frame cannot use the world-point cache (125 → 12 fps on KITTI's 1.5 M points).

Pacing modes: `capture` plays the input's own clock but reveals each submap the moment its last frame was taken, i.e. pretending zero latency; `wall` replays the measured processing times; **`realtime`** is the honest one — input and tracked camera run on the capture clock while each submap appears when it actually arrived, so the map visibly trails the camera by the pipeline's real lag (measured median 3.4-4.6 s, max 6.5 s at submap 16). It needs a recording made with `--tracking --realtime`, where the camera is driven by the per-frame tracker and the trail is optimised keyframes for the past plus the live tracked tail; `--pacing auto` (the default) selects it whenever the recording supports it. **There is one trail, it is drawn live, and it is corrected in place** (`_init_live_trail`/`_advance`). A vertex per *input frame*, never replaced, only moved: while the pipeline is still working on a stretch, its vertices sit where the tracker put them in real time; when the submap covering them lands, their target becomes the optimised estimate and they ease into it. So the line the viewer watched being drawn live is the same line that then bends into the corrected shape. The earlier design — optimised keyframes for the past plus a separate live "tail", with `--live_camera auto` switching wholesale above 80% coverage — is gone: it waited for a submap and then swept along the finished trajectory, which is exactly what it looks like, and the handover deleted the live stretch rather than correcting it. Measured on-screen lag (input frame minus marker frame) fell from the full pipeline latency to **0.00 s median on chess and Replica, 0.47 s on teddy**, with the marker live-driven on 83-100% of frames, worst single-frame marker jump 5-11 cm.

The raw pose stream still needs cleaning — `_build_live_path` rejects gross PnP outliers against a robust speed bound (a single-frame 3.7 m jump was measured; it also throws out the 1e38 garbage described above), interpolates dropouts shorter than `--live_gap`, and smooths translation *and* rotation with a **centred** window (`--live_smoothing`, default 0.25 s; offline rendering can use the future, so it costs no lag — jerk p99 falls 149 → 25 mm). Rotation needs it too, since the marker's orientation now comes straight from this stream.

**The trail may never run ahead of the marker.** It used to be drawn to the current input frame while the marker sat at `_cam_seq`, so the line grew first and the camera chased it — it was showing poses the marker had not reached. It is now clipped to the marker's own frame.

**`--live_trust` decides whether the live stream is drawn at all.** The tail exists to show the stretch the map has not reached, i.e. one map latency of motion; if the tracker's error is larger than that stretch, it conveys nothing and actively misleads. The test is median live-vs-map error divided by the distance the camera covers in one map latency: chess 0.02, Replica 0.09, teddy 0.15, **KITTI 1.22** — so KITTI's live stream is rejected and the map drives everything, which took its worst single-frame vertex motion from 7.40 m to 0.56 m and frames moving over 1 m from 333 to **0**. A rolling live->map similarity was tried first and **removed**: the disagreement is accumulating drift, not a fixed gauge offset, so a global fit did not reduce it (KITTI 59.7 -> 61.0 m) while every re-fit shifted the whole tail at once (worst vertex move 7.4 -> 14.8 m). `--live_fill` interpolates interior trail vertices that have neither a live pose nor map coverage, so the line stays continuous across a dropout instead of jumping it; it changes the drawn shape only, and no metric here captures it.

A map-driven marker is **drawn dimmed and hollow** so a hold reads as "tracking lost, the map is driving" rather than as a frozen video, and `--live_catchup_max` (default 3) caps how fast it may close a gap, since an exponential close starts fast enough to look like a leap. Neither hides anything: dropouts are multi-second when they happen (teddy 3.7-4.0 s, KITTI up to 32 s) and there are no short ones to interpolate across, so the only alternatives are to show the hold or to invent motion.

Three rules keep the marker honest through a dropout, and each one was a measured failure first. It **never moves backwards and never teleports**: at the moment tracking dies the marker is at the live head while the map covers only `head - latency`, so it holds. It then follows the map's **frontier sweep**, not the map's coverage — coverage advances as a staircase, one submap at a time, and following it directly froze the marker for a whole submap interval (11 s on KITTI) and then lurched. When tracking resumes it closes the gap on a **time constant** (`--live_catchup`, default 2 s) rather than at a fixed multiple of real time, which left KITTI crawling 13 s behind. Coverage percentage turns out to be the wrong thing to fear: the gap *structure* is what matters, and it is far kinder than the headline number — chess (78%) and Replica (81%) have a maximum gap of 1-2 frames, teddy (66%) has one 5 s hole, and KITTI's 34% is one 57 s hole plus a start-up gap, with a median gap of 1 frame everywhere.

**KITTI is the honest failure case.** Its live stream is a real estimate — 44.9 m RMSE against ground truth over a 1233 m path, 3.64% — but the map on the same run is 8.2 m (0.66%), and more importantly the tracker **under-scales translation by 14% relative to the map** (over a matched stretch: GT 246 m, map 177 m, live 153 m). That is not a frame-convention bug, and it is not post-hoc correction: the live stream sits a median 58 m from the map *as the map stood at the time*, from the very first submap. It accumulates into corrections of a couple of hundred metres, so KITTI needs `--correction_ease 3.0` and still shows the live line being visibly dragged into place. Framing has to account for it too — `_fit` includes the live vertices, or the live line leaves the frame on the right.

Framing is solved for the run (view azimuth across the trajectory's principal axis, distance from an exact frustum fit, inset corner and HUD bars excluded from the safe area), so it needs no per-sequence tuning. The container has no `ffmpeg` binary, so it encodes with OpenCV's mp4v there and with libx264 on the host — rendering on the host (`--render_only`) roughly halves the file size, and `--target_mb` caps the file size (capped CRF: constant quality, degraded only where that would overshoot). The framing ease settles in finite time rather than decaying exponentially — an ease that never arrives creeps the whole cloud sub-pixel forever, which is invisible but doubles the file, since no block can be skipped. Host renders cannot write into the Docker-root-owned `outputs/`, so they go to `videos/`.

`da3_slam/frontend/tracker.py` is the **low-latency pose layer** (`tracking.enable`, `--tracking`; off by default). DA3 cannot pose a frame until its batch is complete, so poses arrive one submap at a time — measured on fr1/teddy at the shipped config: updates every 8.0 s, each ~5.8 s after the fact. The tracker adds the usual fast-tracking/slow-mapping split: Lucas-Kanade carries ~1200 features frame to frame, the processing thread publishes the newest optimised keyframe's depth as a `TrackingReference`, and every frame solves PnP against it — pose lag 6 s → ~11 ms for ~9-11 ms/frame of CPU. It never enters the pose graph, so the map and every benchmark number are untouched. Two things are load-bearing. **The reference is one DA3 inference old**, so the tracks seeded before it must still be alive: survival over that gap is the whole ballgame (1200 features, teddy: 124 tracks at 2.6 s, 17 at 5.8 s), which is why tracking pairs with `submap_size` 16 and degrades at 32 on fast handheld. **Replenishment** (`_replenish`) reprojects keyframe clouds into the current frame so tracks born *after* an observation set was made also acquire 3-D — without it the set only shrinks and coverage on teddy falls 51% → 23%. It runs over a **local map** (`local_map_size`, default 12 keyframes, `replenish_keyframes` scanned per frame), and observations are held in **world coordinates** tagged with the keyframe they came from: that is what lets several keyframes feed one PnP, and what lets `_register` move them when the graph corrects (the transforms ride along on each new reference in `TrackingReference.updates`, or the local map silently drifts out of agreement with the map it came from). A **constant-velocity motion model** (`_predict`) extrapolates across gaps up to `motion_model_frames` and warm-starts PnP while tracking is continuous. A velocity gate on top of it was tried and reverted — gating on the previous *accepted* pose fed relocalisation back into itself. The gate that ships instead is `_plausible`, which bounds the solved camera against the observation cloud that produced it (`max_cloud_radii`, default 10): degenerate correspondences make PnP return a finite but absurd camera that `np.isfinite` cannot catch, measured as a run of **89 consecutive Replica frames reaching 1e38 m** — a tenth of that sequence's live poses. They never reached a video (`make_video`'s outlier gate dropped all 89) but the tracking benchmark would have scored them, so live ATE measured on Replica before this fix is suspect. Bounding against the cloud rather than against velocity is what keeps it non-recursive. Measured at submap 16, 900 frames paced at 30 fps: Replica office3 64% coverage / 5.1 cm, teddy 31% / 9.9 cm; ~23 points of the shortfall is the start-up gap before the first submap exists, and the rest is fast-motion dropout, where it reports no pose rather than a wrong one. When a fast-motion burst wipes the track set, `_relocalize` matches the reference image straight into the live frame (at the reference's own resolution — upscaling DA3's processed image softens the very corners it depends on) with a forward-backward gate loosened by `reacquire_fb_scale`, and registers the survivors as new tracks. Two traps it took measurements to find: the corner mask must encode *every* condition the observation has to satisfy later (corners picked on depth alone were then discarded wholesale by the confidence gate, 51 matches → 0 observations), and dead tracks must be pruned from the observation set, which otherwise grew to 5980 entries with 28 alive. That recovery is now **ORB relocalisation** (`_relocalize`), not optical flow: once a burst wipes the track set LK needs a continuity it no longer has, and chaining it to the reference failed on six consecutive attempts. Descriptors need no calibration and no vocabulary — the reference keyframe is known, so it is a 1-vs-1 match, and DA3 already supplies its depth and intrinsics. It runs at each reference the chained tracks did not survive to, and every `relocalize_interval` frames while lost. Coverage: teddy 21→36%, chess/seq-03 47→65%, Replica office3 83→84%, and cost *fell* 10.5 → 7.3-7.8 ms/frame. Three measurements shaped it. The textbook Lowe ratio of **0.75 is far too strict here** (10-75 geometrically consistent matches over 1-7 s baselines, versus 41-218 at 0.90). Looser matching lowers the inlier fraction to 10-20%, which **100 RANSAC iterations cannot find** — hence `ransac_iterations: 1000`, free in the steady state because RANSAC stops at its confidence. And the observation set **must be pruned to the RANSAC inliers** after every solve: without that it fills with outliers, the inlier fraction never recovers, RANSAC burns its full budget on every later frame, and the tracker degrades to 23 ms/frame with a 1.4 s pose lag — the opposite of its purpose. The accuracy cost of loose matching is real (teddy median 9.8 → 15.8 cm) and is what the local map then buys back — measured on teddy at matched settings, one keyframe gives 39% coverage at 34.4 cm while three give 23% at 8.4 cm, i.e. the local map is *stricter*, rejecting poses the single-keyframe version happily reported. Do not expect it to raise coverage: the measured failure is RANSAC rejecting correspondences (relocalisation itself succeeded on 287 of 287 attempts), so what limits coverage is correspondence *quality* under motion blur, not which keyframe is used. The map is unaffected throughout, since tracked poses never enter the graph. `scripts/test_tracker.py` checks the geometry against a synthetic plane with no GPU, including the recovery path. **`scripts/benchmark_tracking.py` is how tracking changes are judged**: it scores the *live* pose stream against ground truth through `benchmark_common` (same ATE machinery as the map benchmarks) and prints the optimised trajectory's ATE on the same frames beside it, so "the tracker got better" is a number rather than a coverage percentage. Coverage alone is actively misleading — a single-keyframe configuration scored 39% coverage while being wrong by 34 cm. On fr1/teddy the live stream sits at **32.5 cm Sim(3) ATE against the map's 1.23 cm on the same frames** (ORB, 26% coverage), which is the real size of the gap. Anything measured before the observation-array fix below is not comparable. It needs `--realtime`-style pacing, which it does internally.

**The tracker's start-up gap is a batch-size problem, not an inference-latency problem.** Before the first submap is optimised there is no reference, so `_intrinsic()` has no K and nothing can be solved — measured at `submap_size` 16 the dead time is 14-22% of a clip (teddy 7.3 s, chess 7.3 s, Replica 10.8 s, KITTI 15.2 s), and **60-85% of it is spent COLLECTING the first batch** (4.2-12.7 s) rather than waiting for DA3 (2.4-3.3 s). So the lever is `submap_warmup_size`, which already exists. Measured at submap 16, XFeat + full local map, `--lockstep 1` for determinism:

| | time to first pose | tracker coverage | map ATE Sim3 | map scale |
|---|---|---|---|---|
| teddy  w16 / w8 / w4 | 8.6 / **4.3** / 4.3 s | 65.7 / **82.2** / 68.5% | 0.0475 / **0.0387** / 0.0388 | 1.082 / 1.115 / 1.142 |
| chess  w16 / w8 / w4 | 8.5 / **4.3** / 4.3 s | 74.4 / **87.2** / 87.2% | 0.0387 / 0.0403 / 0.0390 | 0.950 / 0.979 / 0.977 |
| Replica w16 / w8 / w4 | 15.0 / 7.6 / **4.3** s | 66.8 / 84.9 / **89.5%** | 0.0071 / **0.0060** / 0.0075 | 1.000 / 0.970 / 0.963 |

`submap_warmup_size: 8` halves the dead time and buys 10-18 points of coverage, and the Sim(3) ATE penalty the batcher docstring warns about **did not reproduce** here — it is flat on chess (+4%) and better on teddy (-18%) and Replica (-15%). The cost shows up in **metric scale** instead, which is the part of the warning that does hold: Replica's scale goes 0.9999 -> 0.9698 and its SE(3) ATE 0.0069 -> 0.0436 m, teddy's scale 1.082 -> 1.115 with SE(3) 0.0840 -> 0.1037 m. Sim(3) absorbs that, so it only matters for metric output — but this system's claim *is* metric scale, so do not take warmup 8 as free. Going to 4 buys nothing further except on Replica and costs more scale again (teddy SE(3) 0.1274 m). On live accuracy there is no systematic trend once the coverage confound is removed (common-frame live ATE, teddy 29.8/40.0/26.5 cm, chess 11.9/14.0/14.2, Replica 132.9/33.8/24.2 — Replica's w16 figure is the tracker blow-up, which a smaller first submap avoids). Grid: `scripts/benchmark_tracking.py --warmup_size N --lockstep 1` (which also prints time-to-first-pose) beside `benchmark_{tum,7scenes,replica}.py --submap_warmup_size N`.

**The live tracker runs on its own thread** (`_tracking`), and the frontend hands frames over through a bounded, LOSSY queue rather than tracking inline. This matters more than it sounds: tracking was the single largest cost in a paced run — **49.0 s of a 70.3 s teddy recording, more than DA3's own 33.4 s** — and it was paid on the frontend thread *ahead* of keyframe selection, so every millisecond of it delayed batching and inflated the map's latency. Tracked poses never enter the pose graph, so when the tracker falls behind the correct answer is to drop the frame, never to hold the frontend. The sentinel is sent from the frontend's `finally` and must not block (a bare `put()` on a full queue after the tracking thread has died would hang the run — the loop-closure sentinel bug again).

Measured on teddy, 47.3 s of footage, going from `submap_size` 16 + inline tracking to **24 + decoupled**:

| | before | after |
|---|---|---|
| per-submap latency | 4.5 → 14.4 s, **growing** | 3.5-8.0 s, **flat** |
| post-input drain | 15.3 s | 8.6 s |
| wall clock | 62.6 s | 55.9 s |
| map ATE Sim3 | 0.0475 | **0.0373** |

Growing latency is the signature of a backlog; flat latency means the pipeline keeps up. `submap_size` is the other half of it, and it is not a trade — bigger is both faster and more accurate, because fewer submaps means far fewer loop-closure re-inferences. Measured offline on teddy: size 16 → 13 submaps, 20.4 s of loop closure, 59.0 s total (1.25x real time), ATE 0.0475; size 24 → 9 submaps, 13.3 s, 48.8 s (1.03x), 0.0373; size 32 → 7 submaps, **6.1 s**, 41.1 s (**0.87x**), **0.0276**; size 48 adds nothing (0.88x, 0.0281). Submap *building* is nearly flat across all of them (38.6 → 35.0 s) — the same keyframes go through DA3 either way — so **the entire throughput win is loop closure**. The catch is that the latency FLOOR is batch fill time, which rises with submap size (3.7 s at 16, 5.9 s at 24, 8.0 s at 32), so 24 is the balance and 32 is for when map accuracy outranks on-screen lag.

**`tracking.queue_frames` trades pose lag for coverage, and nothing else.** It never touches the map, since the frontend does not wait on this queue. Measured on teddy at submap 24: depth 2 → 48.4% coverage / 29.4 cm / 22 ms pose lag; depth 8 → 47.2% / 32.3 cm / 24 ms; depth 64 → **61.9% / 28.3 cm** / 450-616 ms. For an offline video the lag is free — poses are stored by `seq_idx` and replayed on the capture clock, so a late pose still lands in the right place — which is why recordings use 64 while the default stays at 8 for a genuinely live consumer. Making the tracker *cheaper* does not buy coverage: `replenish_keyframes` 10 → 4 and `local_map_size` 400 → 60 cut cost 26.5 → 19.5 ms/frame but left coverage at 43-47% throughout, and the cheapest arm was much less accurate (45.0 cm vs 30.4). Cost was never the binding constraint; queue depth was.

**The bootstrap ladder** (`tracking.bootstrap`, `--bootstrap`; off by default) attacks that dead window without touching the map. Before the first submap exists, DA3 re-runs on the first 2 keyframes, then 4, then 8, each at `provisional_resolution`, purely to seed the tracker — `_KeyframeBatcher.bootstrap()` emits the rungs, `_publish_bootstrap_reference` places them. The first rung *defines* the frame (DA3's own batch poses, scale 1, which is the gauge the graph will prior frame 0 into anyway); later rungs chain onto it through the keyframe they all share, by the median depth ratio at that anchor — the same bridge consecutive submaps use. **None of it reaches the pose graph**, which is the whole point versus `submap_warmup_size`: the map keeps a full-size first batch and the metric scale chain is untouched. Measured paced, 2 repeats, submap 16, XFeat + full local map:

| | time to first pose | tracker coverage | map ATE Sim3 | live ATE, common frames |
|---|---|---|---|---|
| teddy | 7.3/6.9 → **4.3/4.3 s** | 64/68 → **70/71%** | 4.53/4.87 → 4.69/4.46 cm | 27.9 → **36.6 cm** |
| chess | 7.3/6.9 → **4.3/4.3 s** | 78/79 → **86/87%** | 4.10/4.10 → 4.00/4.02 cm | 21.3 → 23.1 cm |
| Replica | 10.9/10.5 → **4.8/4.4 s** | 78/82 → **87/91%** | 0.56/0.60 → 0.59/0.63 cm | 42.9 → 47.9 cm |

So it halves the dead window and adds 4-9 points of coverage at **zero cost to the map**, which `submap_warmup_size` could not do. The cost is live accuracy on teddy: 27.9 → 36.6 cm on the frames every run answered, consistent across both repeats, where chess (+8%) and Replica (+12%) are inside this benchmark's noise. The likely mechanism is that the handover correction is a single Sim(3) fitted over the rung's keyframes, and the bootstrap-to-map difference is not exactly a similarity, so the first ~130 frames stay slightly misplaced and drag the global alignment.

Two things this cost real time to learn. **The handover must rewrite the poses already emitted**, not just re-register the tracker's observations: `_register` moves the local map into the optimised frame on its own, but the poses already handed to the consumer were solved in the ladder's gauge, and a single Sim(3) alignment cannot fit two gauges at once — leaving them there put chess's live ATE at 42.1 cm with *every age bucket* degraded, versus 11.7 cm once `_reconcile_bootstrap` emits the correction through `on_pose_correction`. The bound is "everything emitted so far", not the last rung's keyframe. And the correction must be **queued, not applied** (`set_correction` → next `step()`): applying it from the processing thread dropped references out from under `_replenish` in the frontend thread and raced into a `KeyError`. **Do not measure this with `--lockstep`**: before the first batch exists nothing throttles the frontend, so it sprints to the first batch boundary while the rung's DA3 call runs, and the ladder is structurally invisible (first pose 128 either way). Measure paced, with repeats.

Videos recorded with `--tracking_set bootstrap=true` need one renderer change to show any of it: `render()` used to return a blank frame whenever no submap existed yet, which is exactly the window the ladder fills, so the gain was invisible on screen. It now draws the live trail and marker there, framed from the first snapshot's fit. Recorded coverage with the ladder on: chess 87%, Replica 91%, teddy 72%, KITTI 39% (the KITTI tracker solves nothing before the handover — 0 poses rewritten — so the ladder buys it only the coverage that follows).

**Reference age is what sets live accuracy**, and `tracking.refresh_keyframes` is the lever on it. Measured on fr1/teddy by bucketing live-vs-map error on the age of the reference the tracker was actually solving against: 0.15 m at 2-4 s, 0.22 m at 4-6 s, 0.29 m at 6-9 s — and most frames sit in the old buckets, because the reference only refreshes when a submap lands. With `refresh_keyframes > 0` the provisional path fires *repeatedly* instead of once per batch, re-inferring the shared anchor plus the newest `provisional_window` keyframes so the cost stays flat rather than growing with the batch. Measured at submap 24 with the bootstrap ladder, 2 repeats, **on the 201 frames every run answered** (whole-stream ATE is useless here — coverage moves between arms, and the same configuration measured 14.6 and 30.1 cm on two runs):

| | common-frame live ATE | extra GPU over 47.3 s |
|---|---|---|
| refresh 0 (once per batch) | 31.2 / 32.1 cm | 1.5 s |
| refresh 8, window 8, res 392 | 24.6 / 26.5 cm | 14 s |
| refresh 4, window 8, res 392 | 17.3 / 13.4 cm | 30 s |
| **refresh 4, window 4, res 280** | **14.4 / 16.9 cm** | **9.5 s** |

So a reference refreshed every 4 keyframes **halves the live error** (31.7 → 15.6 cm), and the small-window/low-resolution variant matches the expensive one at a third of the GPU. Repeats are tight within an arm once the coverage confound is removed, which is the only way this benchmark says anything.

**The refresh needs `merge_observations` or it makes the camera worse, not better.** `_observe` used to REPLACE the whole observation set on every adopt and reset the PnP warm start — correct when a reference arrived once per submap, since what it discarded was stale, but with a rolling refresh it fires several times per submap and each replacement threw away the accumulated multi-keyframe local map and forced a cold solve. Measured on teddy: live-pose jerk p99 rose 120.7 → 176.4 mm (an erratic-looking camera), dropouts went from 5 covering 17% of the clip to 6 covering 24%, and coverage fell 66% → 55%. Observations are in world space, so keeping the live ones across a reference switch is sound.

How much history to keep is a straight **accuracy-versus-stability** trade, and it is sharp (common frames, 2 repeats):

| | common-frame ATE | coverage | dropouts |
|---|---|---|---|
| no refresh (baseline) | 26.1 cm | 66% | 5, 17% of clip |
| refresh 4, no merge | **16.8 cm** | 55% | 6, 24% |
| refresh 4, merge age 4 | 17.1 cm | 57% | 6, 25% |
| refresh 4, merge age 12 | 45.1 cm (one run 74.8) | 58% | — |
| **refresh 4, merge unbounded** | 25.5 cm | **75%** | **3, 10%, none over 2 s** |

Bounding the age keeps the refresh's accuracy and gives back the coverage; leaving it unbounded does the reverse, and is the default (`merge_max_age: 0`) because the stability is what shows on screen: no dropout longer than 1.83 s, against multi-second ones in every other arm, at an accuracy no worse than the pre-refresh baseline. Age 12 is unstable and should not be used. Note the refresh *raises* jitter however it is configured (jerk p99 120.7 → 166.9 mm even with merging), though the renderer's centred smoothing hides nearly all of it — rendered jerk p99 is 16.3 mm at `live_smoothing` 0.25 and 7.6 mm at 0.5.

**The refresh is not universal — apply it where coverage is poor, not where it is already good.** Recorded on the same configuration: Replica went from 2 dropouts covering 8.0 s to **zero**, coverage 80% → 94%; teddy went from 5 dropouts (17% of the clip) to 3 (10%), coverage 66% → 75%. Chess went the other way — **0 dropouts to 3** covering 21% of the clip, coverage 87% → 58% — because chess was already clean and the extra inference only contends for the GPU its tracker needs. Chess therefore ships with `refresh_keyframes: 0`. This is the same pattern every tracker lever in this file shows: it helps where coverage is low and hurts where it is high.

The cost is paid in the other two priorities, and it is real: the extra inference competes with submap building, so map latency rises from a median 5.9 s to 7.2 s (it stays FLAT — no backlog returns — and wall clock goes 55.9 → 56.7 s), and tracker coverage falls 66% → 55% because provisional inference contends for the GPU the tracker also wants. The map itself is untouched, since none of this enters the graph.

A **blur gate** (skip solving frames much softer than the recent median, let the motion model carry them) was built and **measured worse**: 19.75 cm vs 12.61 cm live ATE on teddy at equal coverage (both pre-fix, but the comparison was like-for-like). A blurred frame's PnP solution beats extrapolating over it — RANSAC already filters what the gate was meant to catch. It ships disabled (`blur_ratio: 0.0`) rather than deleted, so the result can be re-checked with `--no_blur_gate`.

`matcher: xfeat` swaps ORB for XFeat in the relocalisation path (`da3_slam/frontend/xfeat_matcher.py`, loaded via `torch.hub` into the persisted TORCH_HOME cache — nothing vendored, no weights in the repo). Measured on teddy frames it finds 2-3x more geometrically consistent matches than ORB at the 1-3 s baselines relocalisation actually runs at (451 vs 217 inliers at 1 s, 182 vs 56 at 3 s), and end to end it **more than doubles coverage, 26% -> 61%**. It is not the default, for two reasons the isolated benchmark did not show: live ATE got *worse* (32.5 -> 59.6 cm — the extra poses are the marginal ones), and pose lag went 10 ms -> 480 ms, because inside the pipeline XFeat contends with DA3 for the GPU (6 ms standalone, far more under load). On CPU it is not an option at all: ~1055 ms per call versus ~6 ms on the GPU.

**Provisional inference** (`tracking.provisional`) runs DA3 on the first half of each batch at `provisional_resolution` purely to refresh the tracker's geometry sooner, placing it in the world frame through the anchor the batch shares with the previous submap — never through the pose graph. It ships **off**, but NOT because it was shown to fail — that verdict was withdrawn once the noise was measured. A single A/B put it at 40.2 cm RMSE against 10.9 cm on the frames both answered for, which looked decisive; three repeats of the *baseline* alone then measured 29.2 cm +/- 9.3 on a common frame set, so 40.2 is about 1.2 sigma out and means nothing. It is off because it costs 25% GPU duty for an unproven benefit. The GPU cost is as estimated (+25% duty, 11.8 s over 47.3 s of footage). chess/seq-03 and Replica office3 *looked* better with it (57.9 → 12.2 cm, 32.2 → 27.4 cm) but both changed coverage at the same time, so those comparisons are confounded.

**The tracking benchmark is not deterministic, unlike the map benchmarks — and the spread is large.** Three repeats of one configuration on fr1/teddy measured coverage 30.7% +/- 4.6 (24-35) and live ATE 32.9 cm +/- 11.0 (18-44); restricted to the 337 frames every run answered, 29.2 cm +/- 9.3 (18-41). So **1 sigma is about a third of the value**, and a comparison needs roughly a 2x gap or several repeats before it means anything. Pacing is the cause: wall-clock thread timing decides when references land and which frames get tracked. `--repeats N` reports the spread and the common-frame figure; use it before believing any tracker change. Several single-run comparisons made while building this layer do not clear the bar and should not be quoted.

Two bugs found by this harness, both of which had been corrupting earlier measurements:
1. **The loop-closure sentinel leaked on every error path.** `_processing` returned early when another thread had failed, skipping `loop_closure_queue.put(None)`, so the worker blocked on its queue forever, `run_stream`'s join never returned, and the run **hung instead of raising** — the real exception was invisible. It is now sent from a `finally`. Any pipeline hang with three live threads (main joining, worker on `queue.get`, tqdm) is this shape.
2. **The tracker's four parallel observation arrays were pruned two at a time** in `_flow`, left over from before observations moved to world space. It only fired when an adoption failed right after a prune, so it looked intermittent, and it silently produced wrong world points before it crashed. `_check_observations` now asserts the invariant. **Offline, tracking needs `--realtime`**: an unpaced replay runs the frontend to the end of the sequence before the first submap is optimised, so nothing is ever tracked (run_slam warns).

There is **no pytest suite and no linter config** (a `Makefile` and `docker-compose.yml` exist for the Docker workflow above; the pipeline itself is still driven by the `scripts/`). The `scripts/test_*.py` files are runnable smoke/integration scripts, not a unit-test framework (`test_pose_graph.py` and `test_keyframe_selector.py` run without a GPU; `test_submap.py`, `test_loop_closure.py` and `test_token_hook.py` need DA3). They share `scripts/smoke_test_utils.py` (header/check/image helpers). Shared evaluation code is layered: `scripts/benchmark_common.py` is the dataset-agnostic benchmark standard (dataset I/O, ATE/RPE metrics, output schema — copied verbatim across the SLAM/ workspace repos, so edit it in lockstep or not at all); the `benchmark_*.py` drivers combine it with the `scripts/da3_runner.py` adapter (`SharedSLAM` model reuse, standardized run interface); `scripts/tum_eval_common.py` adds `SharedSLAM`/`evaluate_sequence`/`average_metrics` for the TUM study scripts (`ablation_tum.py`, `kf_submap_grid.py`) and re-exports the metrics from `benchmark_common`. Model aliases accepted by the eval scripts: `nested-giant` (default/best), `giant`, `large`, `base`, `small`, or a full HuggingFace ID.

EuRoC support has two entry points sharing the dataset I/O in `scripts/benchmark_common.py` (auto-discovers `mav0` incl. the doubly-nested `<seq>/<seq>/mav0` unpack; loads cam0 frames; converts GT from the IMU/body frame to the camera frame via `T_BS` from `cam0/sensor.yaml`, GT quaternions are `w,x,y,z`; optional radtan undistortion). `scripts/euroc_common.py` re-exports those loaders and adds the TUM-format GT conversion glue (`ensure_euroc_gt_tum`) used by `evals/convert_euroc_gt.py`:
- **`scripts/benchmark_euroc.py`** — in-house ATE/RPE (mirrors `benchmark_tum.py`), undistorts by default (`--no_undistort` to skip), timestamps in seconds.
- **`evals/eval_euroc.sh`** — evo-based harness (mirrors `eval_tum.sh`): runs `run_slam.py` on the raw `mav0/cam0/data` frames, then `evals/convert_euroc_gt.py` writes a camera-frame TUM GT in **nanoseconds** to match run_slam's filename-derived timestamps, and `evo_ape ... -as --t_max_diff 20000000` (20 ms) scores it.


Monocular scale is arbitrary, so the **Sim3-aligned ATE** (evo `-as` / `--correct_scale`, or benchmark_euroc's Sim3 column) is the headline metric.

## Configuration model

`config/default.yaml` holds **all authoritative defaults**. All config dataclasses (`SLAMConfig`, `NoiseConfig`, `LoopClosureConfig`) live in `da3_slam/config.py` except `KeyframeSelectorConfig` (next to its component); the component modules re-export their config class. **`da3_slam.config` imports without the GPU stack** (no torch/gtsam/DA3) — `da3_slam/__init__.py` is lazy (PEP 562), so config loading and CLI `--help` work on machines without CUDA. The flow is:

1. `scripts/run_slam.py` loads the YAML to seed `argparse` defaults, then parses CLI overrides on top.
2. `da3_slam.config.load_slam_config(yaml_path, **overrides)` builds the typed `SLAMConfig`. Only **top-level scalar** keys can be passed as `overrides`; nested keys (keyframe/noise/loop_closure) are read straight from the YAML, so boolean/nested CLI flags are applied by mutating the returned config object afterward (see `build_config()` in `run_slam.py`).

When adding a tunable parameter: add it to `config/default.yaml`, to the relevant `@dataclass` in `da3_slam/config.py` (or `KeyframeSelectorConfig`), thread it through `load_slam_config()`, and optionally expose a CLI flag in `run_slam.py`.

Loop closure thresholding is an **L2 distance** on DINO-SALAD descriptors (`loop_closure.distance_threshold`, lower = stricter). The CLI flag is `--loop_distance_threshold` (`--loop_threshold` is kept as an alias).

## Pipeline architecture

The runner is `da3_slam/slam.py` → `DA3SLAM.run()`. It executes **four daemon threads** communicating over bounded `queue.Queue`s (a `_RunContext` dataclass holds all shared state, queues, timings, and a shared `backend_error` for cross-thread failure propagation):

```
_frontend  →(batch_queue)→  _inference  →(submap_queue)→  _processing  ⇄(loop_closure_queue/loop_closure_result_queue)⇄  _loop_closure_worker
```

- **`_frontend`** (`frontend/keyframe_selector.py`): `OnlineKeyframeSelector` uses Lucas-Kanade optical flow; a frame becomes a keyframe when mean tracked displacement exceeds `min_disparity_fraction * W`. Optional blur gating (off by default; live demo on): in segment mode `sharpness_window` swaps each stride-picked keyframe for the sharpest frame (Laplacian variance) within ±window; in disparity mode `min_sharpness_ratio` defers keyframes much blurrier than the recent median (the max_submap_size force still fires, so sustained blur cannot stall the pipeline) — motion blur degrades DA3 poses, retrieval descriptors and repair re-inference all at once. Keyframes are batched into groups of `submap_size`. **Each submap shares its last keyframe as the first frame ("anchor") of the next submap** — this 1-frame overlap is structurally load-bearing (see below). (`KeyframeSelector` is a batch wrapper around the online selector for scripts.)
- **`_inference`** (`backend/inference/`): `SubmapBuilder` runs DA3 (`DepthEstimator` wraps `depth_anything_3.api`) on each keyframe batch, confidence-filters point clouds with **one threshold computed globally across the batch** (`confidence_percentile`), and produces a `Submap` of `Frame`s. Optionally attaches CLIP `semantic_vector`s via `SemanticEmbedder`.
- **`_processing`** (`backend/processing/factor_graph.py`): builds the GTSAM `PoseGraph` incrementally — one SL(4) node per keyframe keyed by `seq_idx`, between-factors for consecutive frames, a tight prior on frame 0. Runs incremental `optimize()` after each submap and a final optimization at the end.
- **`_loop_closure_worker`** (`backend/processing/loop_closure.py`): `LoopClosureDetector.process(submap)` matches per-frame DINO-SALAD descriptors against all previous frames (top-K priority queue, `min_submaps_apart` gap), re-runs DA3 on each matched pair **plus `context_frames` temporal neighbours per side** (multi-view support — bare 2-frame wide-baseline inference is poorly conditioned), gates on mean DA3 confidence over the two matched frames, and returns `LoopClosure` objects carrying `relative_b_to_a` (the measured query→detected cam-to-world transform; the matched frames sit at `query_frame_pos`/`detected_frame_pos` in the re-inference submap). The worker rescales its translation to global metric units and posts a between-factor (`loop=True`) back to `_processing`, which applies a final **geometric sanity gate** (`loop_closure.max_rotation_error_deg` / `max_translation_error`: measurement vs. current graph prediction, generous thresholds) before inserting the factor. Gate failures are **held in a corroboration pool, not dropped** (`_drain_loop_closure_results` + `_HeldLoop`): after an odometry break the graph itself is wrong by exactly the disagreement the gate measures, so when two held closures imply the same correction (translation/rotation consistency, see `_corrections_consistent`) the group is inserted — this is what merges a duplicated map back together. Held closures are re-evaluated against the updated graph on every drain, and one that stays held for `_HELD_ACCEPT_AFTER_DRAINS` drains (≈ submaps) is accepted on its own (uncontradicted; the Huber noise cushions a residual aliased match). Detection-side, `_dedupe_candidates` keeps only the best candidate per detected submap — near-duplicate matches each cost a full re-inference while adding little independent evidence. Separately from retrieval, a detected **boundary break** (scale dead-band fired, or the overlap-2 pose check failed) triggers a **boundary repair**: the worker re-infers a frame pair spanning the broken boundary (`LoopClosureDetector.verify_boundary`) and posts the resulting factor as `trusted` — it bypasses the geometric gate (the frames are known-adjacent; no aliasing risk) and arbitrates the two contradictory boundary factors, rotation included, so segments cannot settle at different angles. Because trusted factors skip the gate, each repair must instead pass `_repair_rotation_deviation`: its rotation is compared against the same relative pose composed through both batches' own chains (via the shared anchor), and a deviation beyond `_REPAIR_MAX_ROTATION_DEV_DEG` (45°) rejects it — low-confidence wide-baseline re-inference can emit ~120° garbage rotations that would corrupt the downstream map orientation. Repairs never fire on benchmarks (they require deadband > 0 or overlap ≥ 2). Loop factors use a **Huber-robustified noise model** (`noise.loop_huber_k`, null = plain Gaussian) so an aliased closure that survives the gates is down-weighted instead of warping the map; `noise.between_huber_k` (null by default, live demo 1.345) does the same for odometry factors — it only acts where the graph has redundancy (overlap≥2 boundary pairs, loop-closure cycles) and concentrates a broken boundary's error at that factor instead of spreading it over the cycle, which is what smears revisited geometry into side-by-side ghost copies.

### Two concepts that are non-obvious and easy to break

1. **Anchor-frame submap bridging (no explicit inter-submap factor).** Consecutive submaps are joined *only* because submap N's last `submap_overlap` frames and submap N+1's first frames are the **same `seq_idx`s** (default overlap 1, VGGT-SLAM style). `_processing` places submap N+1's frames in the global frame by composing the anchor's already-optimized global pose with DA3's local relative poses. `_build_keyframe_poses` dedupes the shared anchors ("first submap wins"). If you change how keyframes are batched in `_frontend`, preserve the overlap or the graph disconnects. With `submap_overlap >= 2` (the live-demo default) the shared frame *pair* is measured by both DA3 batches: `_add_consecutive_frame_factors` deliberately adds the duplicate between-factor (boundary redundancy) and `_check_boundary_consistency` warns when the two measurements disagree — the signature of an odometry break, where a single bad anchor pose used to displace every subsequent submap ("the trajectory jumps and the map rebuilds elsewhere").

2. **Per-submap metric scale accumulation.** Each DA3 batch has its own arbitrary metric scale. `_estimate_boundary_scale` takes the **median depth ratio at the shared anchor frame** between consecutive submaps; this `delta_scale` is multiplied into an `accumulated_scale` that scales the **translation component** of every between-factor (and loop-closure) measurement before it enters the graph (`_scaled_translation`). Loop closures apply an additional depth-scale correction (`_estimate_depth_scale` between the query frame's depth and the loop-closure re-inference's depth) times the query submap's accumulated scale. Rotation is never scaled — only translation. **Note:** `boundary_scale_damping` is **domain-dependent and now ships at 0.0** (full chaining), which is worth −24% Sim3 ATE on TUM and −86% on Replica. It was 1.0 (chain off) until the earlier sweep supporting that value was found to have run with **0–1 loop closures per sequence** — chained scale drift is unconstrained without graph cycles, so that result does not transfer to the tuned system, which closes 3–6. **On aerial/km-scale footage set it back to 1.0**: chaining costs +29..58% on UAS and drives scale to 0.097–0.381, because the boundary ratios there are noisy (12.2% disagreement, 13% of boundaries broken) and compound multiplicatively over hundreds of boundaries. Per-boundary ratio *accuracy* does not predict trajectory error (λ*=1.00 on every domain measured, yet chaining is far worse on UAS end-to-end) — the failure is accumulation, so no per-boundary trust rule fixes it; dispersion-weighted shrinkage was measured over 85 boundaries and falsified (`scripts/measure_boundary_dispersion.py`). **`boundary_scale_deadband`** (default 0 = off; live demo 0.25) handles the regime the sweeps never saw: live D455 runs showed genuine per-batch metric scale *breaks* (boundary translation-unit ratios of 2–6× with near-zero rotation disagreement — the trajectory suddenly stretches and the map rebuilds elsewhere). With deadband d > 0, ratios within `max(r,1/r)-1 <= d` are forced to 1.0 (the sweep-validated behaviour) but a break-sized ratio is applied in full, damping ignored (see `_boundary_delta_scale`).

### Encoder-token tap (Branch C, temporal reuse)

`da3_slam/backend/inference/token_tap.py` reaches inside the DA3 backbone to expose — and optionally replace — the **per-frame encoder tokens**. The tap point is exact, not heuristic: in DA3's ViT block loop (`vision_transformer.py`, `_get_intermediate_layers_not_chunked`) every block with index `i < alt_start` runs *local* attention on a `(b·s) n c` tensor, so **blocks `[0, alt_start)` are a pure per-frame encoder** whose output depends only on (image, resolution) — cross-view attention, reference-view reordering and camera-token injection all begin at `alt_start`. For the default nested-giant that is blocks 0–12 of the 40-block anyview branch; the **metric branch is configured with `alt_start = -1`, i.e. it has no cross-view attention at all** and is frame-independent end to end (a larger reuse opportunity, but it feeds the DPT head from four intermediate layers, so it needs four tap points — currently untapped).

`EncoderTokenTap` attaches `forward_pre`/`forward` hooks to the prefix blocks: it captures the tap block's output per frame, and when tokens are injected it drops those frames' rows before each prefix block and scatters the computed rows back afterwards (a block may **not** return fewer rows than it was given — `process_attention` re-expands with the frame count it captured beforehand). Arming is per-thread (`threading.local`), so a concurrent untapped loop-closure re-inference is unaffected. Nothing in DA3 is patched — that checkout is gitignored and re-cloned by `setup.sh`. Entry points: `DepthEstimator.infer(capture_tokens=…, inject_tokens=…)` and `DepthEstimator.token_tap()`. One cache-validity condition: `InputProcessor._unify_batch_shapes` centre-crops a batch to its smallest frame, so cached tokens are only reusable across batches of the same processed resolution (always true within one sequence; `test_token_hook.py` check 2 verifies it).

### Cross-view token merging (Branch C, the FastVGGT port) — off by default

`da3_slam/backend/inference/token_merge.py` is the other half of the same block loop the tap uses. Where the tap owns the frame-independent prefix (`i < alt_start`), merging owns the **cross-view** blocks: `i >= alt_start and i % 2 == 1` (nested-giant: the odd indices 13–39, i.e. 14 of 40). It ports [FastVGGT](https://github.com/mystorm16/FastVGGT)'s training-free ToMe merging — most tokens are absorbed into a smaller destination set before global attention, and the attention output is scattered back to full length. The kernel is vendored in `_tome.py` (**Meta's VGGT License**, not this repo's MIT — keep its header).

Mechanism is a **module swap**: each global block's `.attn` is replaced by a `MergingAttention` holding the original by reference, reimplementing the attention forward with the merge spliced in after qk_norm and RoPE (FastVGGT's exact position; `qk_norm` is on for precisely the global blocks and LayerNorm does not commute with averaging). Nothing in the DA3 checkout is patched. Two traps: the ViT's attention is `model/dinov2/layers/attention.py`, **not** the near-identical `model/utils/attention.py` (different `head_dim`/`fused_attn` handling — `_verify_upstream()` guards this, since `setup.sh` re-clones DA3); and DA3's global blocks get `pos_nodiff` (all-ones patch positions), so cross-view attention carries no spatial position, which makes merging safer here than in VGGT.

**On/off** (the whole point — it is an experimental compute lever whose baseline is `enable: false`): `--token_merging` / `--no_token_merging` on `run_slam.py` and every `benchmark_*.py`, the `token_merging:` block in `config/default.yaml`, or `SharedSLAM.set_token_merging(cfg)` to flip configs on a model that stays resident. Disabling **detaches** the wrapper entirely. Batches below `min_frames` (default 8) are never merged, which keeps the loop-closure worker's ~4-frame re-inference on the exact path without any thread coordination. `DepthEstimator.token_merging_stats` reports the realised token ratio.

Note `config/default.yaml` now ships **`DA3NESTED-GIANT-LARGE-1.1`** (nested-giant), which does have cross-view attention, so merging applies to it. The older `DA3METRIC-LARGE` default had `alt_start: -1` and **no cross-view attention at all** — merging refuses that model. `scripts/test_token_merge.py` runs kernel checks without a GPU and model checks with one. See `plan_fastvggt-token-merging.txt` for the study design and the first measurements (≈4% faster at submap 16, pose deviation 280× the bf16 noise floor at FastVGGT's default — the speed prize only appears at much larger submaps).

**Benchmarking it** — `scripts/sweep_merging.py` runs the `{merge arms} × {submap sizes} × {repeats} × {sequences}` grid (defaults to UAS) and `scripts/report_merging.py` turns its JSONL into `report.md` + `summary.json` + `merging_agg.csv` + two figures:

```bash
python scripts/sweep_merging.py --seq_dir data/UAS/fyllingsdalen_tunnel data/UAS/runehamar_tunnel/hornbill \
    data/UAS/campus_fog data/UAS/frozen_lake \
    --submap_sizes 16 24 32 48 --merge_starts off 0 7 --repeats 3 \
    --seqcache outputs/sweep/step1_uas_resolution/_seqcache --out_dir outputs/merging
python scripts/report_merging.py --rows outputs/merging/merging_rows.jsonl --out_dir outputs/merging
```

Three things about this sweep are load-bearing. **Keyframes are frozen once per sequence** (at `--freeze_at`, default the largest submap size) and replayed by every cell — without that, `submap_size` also changes keyframe *selection* through `keyframe.max_submap_size`, and any ATE difference is confounded. **OOM is a recorded result**, not a crash: cells that run out of memory are logged with `status="oom"` and their high-water memory, shown as `**OOM**` in the tables and as ghost markers on the frontier plot — a submap size that only runs with merging is the study's central claim. And **`--seqcache`** points at an existing extracted-frame cache, since UAS bag extraction is ~20 GB and idempotent. UAS ATE is reported as **% of ground-truth path length** (`ate_sim3_pct`, from `gt_path_length_m`), the honest metric at km scale; `--max_frames` can truncate before a sequence's GT even starts (frozen_lake's GT begins 43 s in), which the sweep warns about rather than silently scoring every cell `unmatched`.

### Where DA3's GPU memory goes

`scripts/profile_da3_memory.py` attributes the peak to a stage of the forward by sampling `torch.cuda.max_memory_allocated()` at every module boundary (it is monotonic between resets, so the stage during which it last rose *is* the stage that set the peak — no heuristics), and sweeps peak vs frame count and resolution.

```bash
python scripts/profile_da3_memory.py --image_dir DIR --n_frames 16
python scripts/profile_da3_memory.py --image_dir DIR --include "head." --max_depth 2   # drill into the DPT head
python scripts/profile_da3_memory.py --image_dir DIR --scaling \
    --frame_counts 8 16 32 48 64 96 128 --arms fp32 fp32+merge bf16 bf16+merge
```

Measured for nested-giant @504, 16 frames: **peak 11.8 GB = 6.5 GB parameters (55%, 1.69 B of them, all fp32) + 5.3 GB activations**, the activation peak landing in the DPT head's finest full-resolution decoder stages (`scratch.refinenet1`, `output_conv1_aux`). Peak scales as `≈ 9500 MB + 127 MB/frame`, i.e. **80% frame-independent at submap 16** — which is why submap size is memory-gated so hard, and why cross-view attention was never the lever. The metric branch raises the peak by 0 MB (it runs after the anyview working set is released) but keeps 610 MB resident.

Across submap sizes, `peak(MB) ≈ 10272 + 96.8 × frames` (fp32) — the two halves are equal only at N≈106, so **every submap size this system uses is constant-dominated**. The measured wall is between 48 and 64 frames (fp32) and between 128 and 192 (bf16 backbones). Token merging never lowers the peak and *raises* it at long sequences (+16% at N=128, because the merge/unmerge buffers outgrow the shortened attention), so it lowers the maximum usable sequence length; its speedup does grow with length as expected though — 1.01× at N=16 → 1.24× at 64 → 1.51× at 128.

The profile points at one large unused lever: the ViT backbones run under autocast bf16 but store fp32 weights, so casting *only* the two backbones to bf16 cuts peak 40% (11.8 → 7.1 GB) and makes **submap 64 run where fp32 OOMs**. It needs a forward hook casting backbone outputs back to fp32 — DA3 runs its heads under `torch.autocast(..., enabled=False)`, so a bare `.to(bfloat16)` dies with a dtype mismatch in `cam_dec`. **Now adopted** (`backbone_dtype: bf16` is the shipped default): validated on UAS (54.39 vs 55.01 m, 7774 vs 12544 MB) and used for every benchmark number in this repo. See `plan_fastvggt-token-merging.txt`.

## Outputs

`run_slam.py` writes to `--out_dir`: `trajectory_kitti.txt` (12-value rows), `trajectory_tum.txt` (`timestamp tx ty tz qx qy qz qw`; real timestamps inferred from numeric filenames like TUM, else `seq_idx/fps`), `map.ply` (binary, merged colored cloud projected by optimized poses; skip with `--skip_ply`), and `timings.json`. `SLAMResult` (in `slam.py`) owns all the `save_*` methods and `retrieve_best_semantic_frame()` for open-vocab CLIP queries.
